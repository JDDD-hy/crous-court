# REQ-20260910-01：CROUS法庭 v1

状态：Frozen（2026-09-10；OD-03 与 Phase 5 菜品识别/关联规则于 2026-09-11 按产品负责人最新指令定向修订）。延期项必须在对应 Phase 入口前确认，不得改变未被明确修订的 v1 范围。

## 1. 目标用户

- Télécom Paris、ENSAE 及 Palaiseau 周边学生；
- 熟悉“从夯到拉”网络表达，但不一定知道法语菜名；
- 首轮按桌面端完成 Phase 0–8；移动端上传、投票和布局适配在全部既定阶段之后实施。

## 2. 核心任务

用户打开首页后，应立即能够：

1. 审判一份菜品：赞同当前判决或选择自己认可的等级；
2. 查看主食榜和小菜榜；
3. 上传餐盘照片并完成初判；
4. 在不知道菜名时无障碍提交，由社区补名。

## 3. v1 必做范围

### 3.1 餐厅

- `L’Expérimental`：辅助昵称“宿舍 CROUS / All Suites 附近”；
- `Escoffier`：辅助昵称“学校 CROUS / Télécom 附近”；
- 数据库存正式名称，昵称只用于搜索与显示。

### 3.2 内容模型

- 一次用餐 Meal：整张餐盘与地点、日期；
- 菜品 Dish：可复用的菜品概念；
- 出餐 Serving：某菜在某餐厅某日的实际版本；
- 图片 Photo：属于 Meal，可关联一个或多个 Serving；
- 评价 Vote：用户对某个 Dish 选择的目标等级；不同餐厅和日期的同一道 Dish 共享社区等级。

上传按整盘完成，内部拆为 1 份主食和最多 2 份小菜。主食初判必填，小菜名称与初判均可跳过。

同一用户、同一食堂、同一天可提交多张餐盘。每个 Meal 发布时获得案号 `YYYYMMDD-食堂序号-当日展示顺序`；Escoffier 为 `0`，L’Expérimental 为 `1`。案号不依赖审核，内容隐藏后也不复用。

用餐日期不得晚于巴黎当地当天；前端限制日期选择，服务端必须再次拒绝未来日期。主食/小菜菜名默认留空且不提供预设下拉候选，后续识别不得阻塞当前投稿。

### 3.3 菜名未知

- 菜名不必填；
- 可使用“神秘菜品 #编号”发布；
- 支持用户原始描述、正式法语名、中文名和别名；
- 每次 Serving 的原始投稿名均保留，不可被标准名、社区候选、AI 或管理员确认直接覆盖；
- 可使用“神秘黄色主食”“Sauce marron non identifiée”“Plat mystère n°42”等临时名称；
- 其他用户可提交名称候选及证据类型；
- 用户可主动调用自有多模态 LLM 生成结构化菜名候选；AI 失败或未配置时仍可直接发布未知菜品；
- AI 结果必须标记为猜测，与用户最终选择分开保存，不得自动覆盖原始名、确认标准名、合并 Dish 或推断过敏原；
- 现场菜单照片/OCR、外部搜索、视觉 embedding 与自动聚类属于后续增强。

### 3.4 投票

- 投稿者的初判计作第一张真实投票；
- “判得对”保存为当前展示等级；
- “我有异议”必须选择目标等级；
- 每个用户对同一 Dish 只能提交一张有效票，提交前二次确认，提交后不可修改；
- 登录用户在首页看到自己尚未投票的 Dish 时显示 `NEW`；成功投票后立即移除。该状态只按当前会话 User ID 查询，不跨账号共享；
- 社区等级按有序等级的中位数计算；
- 展示各等级票数分布、初判、社区判决和总票数。

固定等级（从好到差）：

1. 夯 🐮
2. 顶级 👑
3. 人上人 😎
4. NPC 🤖
5. 拉爆了 💩

### 3.5 排行榜

- 主食与小菜分榜；
- 首页主食榜权重更高；
- 支持按餐厅筛选；
- “今日套餐”只展示某次 Meal，不参与长期单品排名。

### 3.6 菜品关联与重复投稿

- 排行榜以 Dish 为“嫌疑人”，每位用户的每次餐盘投稿与 Serving/Photo 是该菜的独立“行踪”；
- 同一账号重复提交完全相同的规范图片文件时，以 SHA-256 拦截误操作；不同账号不按图片哈希互相拦截；
- 上传时按标准名、中文名、原始描述和别名提示最多 3 个已有 Dish；用户明确选择后才复用该 Dish；
- 同一道 Dish 在同食堂同日允许多个用户分别投稿并保留各自 Serving；
- 图片相似度、pHash、神经网络 embedding 与 clustering 不作为本阶段合并依据；
- 系统不得自动合并疑似记录；管理员合并/拆分必须保留操作日志且可追溯原始名称。

### 3.7 身份与治理

- 浏览无需登录；
- 上传、投票、补名、举报需要登录；
- 邮箱经去空格及域名小写规范化后作为账号边界；邮箱本地部分区分大小写，同一完整邮箱再次登录必须复用原账号及历史记录，不同邮箱互相隔离；
- 管理员可隐藏餐盘、处理举报、合并/拆分记录、确认名称；
- v1 采用发布后治理，不设置人工发布前审核；管理员由服务端 `ADMIN_EMAILS` 白名单任命，空配置时管理能力失败关闭，不提供站内提权入口；
- AI 可用于内容风险初筛和临时隐藏建议，但不得永久删除、覆盖原名或自动合并 Dish；管理员保留恢复、申诉和最终处置能力；
- 任意登录用户可提交名称候选；同一候选获得 3 个不同账号支持后标为“群众认领”，只有管理员可标为“菜单确认”；
- 上传需确认拥有或获准发布照片，避免出现可识别人脸。

## 4. v1 明确不做

- AI 自动定名、自动合并或后台无感批量识别；
- 自动抓取 CROUS 每日菜单；
- 好友、关注、私信、勋章；
- 长篇评论与复杂推荐系统；
- 自动无审核合并；
- 完整 Three.js/Rapier 体素场景；
- 多校区、多城市和无限餐厅自助创建；
- 站内支付。

## 5. 核心验收标准

- 首屏无需滚动即可完成一次赞同或异议投票；
- 未知菜名也能在合理步骤内完成投稿；
- 投稿可正确关联餐厅、日期、主食和小菜；
- 新投票后社区等级与分布正确重算，重复投票被拒绝；
- 主食和小菜不会进入同一排名池；
- 已有菜品只提示，用户确认后关联，不自动覆盖或合并；
- 补名、三人群众认领、举报、管理员隐藏与合并/拆分形成闭环；
- AI 输出缺字段、超时、限流或未配置时降级为手动填写/未知菜品，不阻塞投稿；
- 关闭动画或启用 reduced motion 后全部功能仍可用；
- 判决动画只在服务端确认成功后触发；同一 Dish 的同一重大结果在单个浏览器会话最多播放一次；
- 桌面端上传和投票可完成；移动端无横向溢出与触控流程验收延期至全部既定阶段之后；
- 未登录写操作被正确拦截；
- 图片和数据库记录可持久化，部署后仍存在。
